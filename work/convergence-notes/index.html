Editing together, apart.

Two people edit the same note on a train and a plane. Both go offline. When they reconnect, nothing is lost and both screens show the same text — without a server deciding who wins.

Three data types, three problems

“Merge two notes” is really three separate consistency problems: character order, tag membership and a scalar title. Each needs a different CRDT, and each has a classic failure mode that only shows up under concurrency.

  • Text needs a total order that every replica derives identically.
  • Tags need add/remove semantics that do not resurrect deleted values.
  • Title needs a deterministic last-writer-wins rule.

RGA: characters as a tree, not an array

Every character is a node with a unique (site, counter) id and a parent anchor. Children of one anchor sort by counter then site, descending. That sort is the whole trick: both replicas compute the same reading order from the same set of nodes, even when the inserts arrived in a different order.

src/rga.jsordering
// deterministic sibling order: newest first, site as the tie-break
children.sort((a, b) =>
  a.counter !== b.counter ? b.counter - a.counter : (a.site < b.site ? 1 : -1)
);

// deletion is a tombstone, so anchors never disappear
deleteNode(doc, id) { doc.nodes.get(id).deleted = true; }

Tombstones are what make the sequence stable: a character deleted on one replica remains a valid anchor for a concurrent insert on another. The cost is memory, and the README says so instead of hiding it.

The OR-Set bug most implementations ship

A naive observed-remove set deletes the whole entry on removal. Merge it with a stale replica and the old tags come back from the dead. This engine keeps retired tags per value and recomputes live membership as (live ∪ live) − (retired ∪ retired). A concurrent add still wins; an observed removal stays removed forever.

src/orset.jsmerge
// union both sides, then subtract everything either side retired
for (const [value, entry] of right) {
  target.live.add(...entry.live);
  target.retired.add(...entry.retired);
}
for (const tag of target.retired) target.live.delete(tag);

Delta sync, not full state

Each operation carries its author and a monotonic sequence number. A peer sends only operations the other vector clock has not seen, so once two replicas are in sync a second exchange transfers exactly zero operations. Clocks also answer causality directly: equal, before, after or concurrent.

Delivery is assumed unreliable. An insert whose anchor has not arrived is buffered and drained when the parent shows up; a delete that overtakes its insert leaves a tombstone that wins later. Both paths have tests.

Fuzzing the schedule, not just the data

Unit tests cover the rules. The interesting failures come from timing, so the fuzzer generates a seeded schedule of edits and partial pairwise syncs, then a full mesh sync twice. Every replica must end with a byte-identical canonical state.

terminalnode bin/notes.js --fuzz 800
seed 20261106 · 800 steps · 4 replicas · 298 inserts, 131 deletes,
73 tag ops, 68 renames, 168 partial syncs
converged: true

The suite runs twenty additional seeds at 130 steps each, plus a state-merge associativity check: merging three snapshots in different groupings must produce the same document.

The demo deliberately deletes “offline ” on one replica while inserting “Today ” on the other. Both edits survive, in a deterministic order, with no coordination and no lost keystrokes.

What it does not do

  • Tombstones are never garbage-collected; documents grow with edit history.
  • Plain text only — no rich-text attributes, cursors or presence.
  • No network transport or persistence layer; the log is in memory.
  • Snapshot merges assume a consistent snapshot per replica.
